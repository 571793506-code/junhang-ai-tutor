# Codex 插件使用边界与优化清单

本文用于把当前 Codex 插件从“默认介入”收缩为“选择性辅助”，避免它继续把生成类、批改类和主观判断类任务拉长。

## 1. 结论

当前项目里，Codex 插件只适合放在三类环节：

1. 高重复。
2. 高规范。
3. 可验证。

不适合放在需要创作判断、主观修正、最终定稿的环节。

## 2. 适用范围

优先保留在这些场景：

- 资料转 Markdown。
- 内容索引重建。
- 上下文拼装和字段校验。
- 编码守卫检查。
- 导出前预检。
- 项目级验证命令编排。

这些工作有共同特征：输入结构清楚、输出格式固定、结果能直接检查。

## 3. 停用范围

以下场景不建议继续用插件主导：

- 生成类内容的主创作。
- 批改类内容的主判断。
- 需要教师主观确认的最终修订。
- 带强上下文依赖的自由写作。
- 模型输出已经明显不稳定时的继续追问和补写。

原则很简单：一旦任务的核心价值是“判断”而不是“执行”，就不要让插件站主位。

## 4. 继续优化的方向

### 4.1 收紧触发条件

- 只在任务类型明确命中时启用。
- 默认不接管所有对话。
- 没有明确结构输入时，先停，不要猜。

### 4.2 输出结构化

插件输出尽量固定成这几项：

- 当前识别到的任务类型。
- 计划执行的动作。
- 校验结果。
- 风险点。
- 是否允许继续。

减少长解释，避免把用户时间花在读过程上。

### 4.3 先预检，再执行

每次关键动作前先做 dry-run 或 preview：

- 先校验输入是否完整。
- 先检查权限和路径。
- 先确认输出是否满足规则。
- 通过后再真正写入或导出。

### 4.4 失败要短路

出现以下情况时直接停：

- 上下文缺失。
- 输入不合规。
- 权限不满足。
- 结构化结果解析失败。
- 已知错误率过高。

不要继续让插件“补一补”，这通常只会放大返工。

### 4.5 减少多轮确认

把常见动作做成固定模板或固定命令：

- 一个任务类型对应一个入口。
- 一个入口对应固定校验链。
- 一个入口对应固定输出格式。

这样用户不用在同一件事上反复解释。

### 4.6 接项目已有校验链

优先挂到现有命令，而不是单独造流程：

- `check:content-context`
- `check:teaching-content`
- `check:content-upload-ui`
- `check:miniprogram-js`
- `check:encoding`

插件只负责把任务送进正确的校验链，不负责替代校验链本身。

## 5. 验收标准

插件优化是否有效，主要看这四项：

1. 单任务平均耗时是否下降。
2. 返工次数是否下降。
3. 错误消息是否更早暴露。
4. 用户是否从“反复修正”变成“最后确认”。

如果优化后仍然把 1 小时的活拉到 3.5 小时以上，说明边界还不够收紧。

## 6. 建议执行顺序

1. 先限制插件只覆盖高重复、高规范、可验证任务。
2. 再把生成类、批改类移出主路径。
3. 然后补结构化输出和 dry-run。
4. 最后再看是否需要进一步拆分入口和减少交互。
