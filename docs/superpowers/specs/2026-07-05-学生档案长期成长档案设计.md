# 学生档案长期成长档案设计

日期：2026-07-05

## 背景

当前学生档案已经能展示教师发布反馈、待巩固内容和学习时间线，但信息量偏少，无法支撑“长期成长档案”的产品预期。现有 API 已经能聚合任务、提交批改、错题、阶段报告、行为日志、AI 问答和课堂互动；问题不在于没有数据源，而在于档案结构仍偏摘要，没有把这些来源组织成家长看得懂、老师能诊断的成长报告。

本设计参考 `E:\UserData\86188\Documents\飞书AI课后辅导机器人` 中学生档案模块的模板经验，但不复制旧项目实现。君航项目内第一版只落地可复用的数据契约、服务端聚合和多端展示边界。

## 目标

- 第一版主入口做“周档案 + 月度综合长期成长档案”双核心展示。
- 周档案负责本周陪伴反馈和下周行动，月档案负责长期成长复盘和阶段诊断主视角。
- 同一份档案同时服务两个核心场景：
  - 家长看得懂：孩子近期学了什么、哪里进步、哪里要跟进、老师建议怎么做。
  - 老师做诊断：用于课后辅导排课、补弱、生成下一阶段任务。
- 档案必须保留教师复核边界：AI 只生成草稿，老师确认后才发布给学生或家长。
- 核心逻辑沉淀在 API、服务层或共享契约中，Web 只作为联调和原型入口，后续微信小程序复用同一结构。

## 非目标

- 第一版不做飞书云文档归档、不做 image 2 图像模板生成、不做期中/期末页面矩阵。
- 期中、期末后续以教师确认后的 PDF 形式生成，并发送给家长查看，不作为第一版学生档案页面的常规展示核心。
- 第一版不把学生档案做成成绩排名、考试战报、预测分或升学风险判断。
- 第一版不把低置信 OCR、未确认分数、未复核错题或模型原始输出写入正式档案。
- 第一版不建立两套独立的老师版和家长版内容。采用同一个结构化快照，按角色过滤可见字段。

## 方案比较

### 方案 A：只扩展页面展示

直接在学生端和教师端页面中增加更多卡片，从现有 `student`、`reports`、`corrections`、`logs` 中拼内容。

优点：最快看到视觉变化。

缺点：核心判断留在 Web 页面状态里，小程序无法复用；教师复核、字段可见性和证据来源容易漂移；长期会继续出现“页面有内容，服务层没有档案契约”的问题。

### 方案 B：扩展现有 profile snapshot

继续使用当前 `/api/students/:studentId/profile/draft`、`/publish`、`/profile`，在 `snapshot` 中增加综合档案字段。

优点：改动较小，兼容当前草稿和发布流程。

缺点：如果只追加字段，没有明确契约和校验，后续会堆成一大块 JSON；不同端仍可能按自己的理解展示。

### 方案 C：建立长期成长档案契约，复用现有 API 流程

定义 `weeklyGrowth` 和 `monthlyComprehensiveGrowth` 结构化快照，服务层负责组装、校验、生成草稿和角色过滤；现有 draft/publish/profile 接口继续承载流程，前端只展示结构化结果。

优点：兼容现有接口，保留教师复核，后续小程序可复用；周档案适合日常跟进，月档案适合长期复盘，期中/期末可以自然扩展为 PDF 交付。

缺点：第一版需要补服务层契约和测试，不能只改页面。

推荐方案 C。第一版只做周档案和月度综合档案两个页面核心，避免一次性把期中、期末、图像模板和云文档都纳入主流程。

## 档案结构

第一版 `snapshot.profileType` 只允许 `weekly_growth` 和 `monthly_comprehensive_growth`。结构分为三层：公共展示层、教师复核层、系统兼容层。

### 周/月定位

- `weekly_growth`：本周陪伴反馈型，展示本周完成情况、一个进步点、一个薄弱点、下周先做什么，文字更短，避免长期诊断语气。
- `monthly_comprehensive_growth`：月度综合成长复盘型，展示整体学习概览、三科总览、重点科目展开、错题闭环、老师下一步和家长配合建议。
- 周档案和月档案使用同一套来源、复核和可见性规则，但内容深度不同。
- 期中、期末不进入第一版 `profileType`，后续单独走 PDF 生成、教师确认和家长发送流程。

### 公共展示层

`publishedView` 只在老师确认发布后给学生和家长展示：

- `periodType`：`weekly` 或 `monthly`。
- `periodLabel`：自然周或自然月展示名。
- `overview`：整体学习概览，周档案 1 句，月档案 1 到 2 句。
- `subjectOverview`：三科总览，数学、语文、英语各 1 条观察；证据不足时写“继续观察”，不编造结论。
- `focusSubjects`：重点科目展开，周档案通常只展开 1 个，月档案选择 1 到 2 个最需要跟进的科目。
- `correctionLoop`：错题与订正闭环摘要，只来自已复核批改和错题记录。
- `stableGrowth`：稳定表现，例如订正配合、能复述题意、能主动追问。
- `tutoringFocus`：老师下一阶段辅导重点，2 到 3 条。
- `parentNextSteps`：家长在家可执行动作，1 到 2 条。
- `timelinePreview`：近期已确认的学习事件摘要，不展示内部审计字段。

### 教师复核层

`teacherReview` 只给教师端使用：

- `sourceCounts`：任务、已复核提交、错题、报告、行为日志、问答、课堂互动数量。
- `evidenceItems`：支撑每个结论的来源摘要，区分任务、批改、错题、问答、课堂记录和老师备注。
- `sampleLimitNotes`：样本不足、科目缺失、时间范围不足等限制。
- `pendingConfirmations`：需要老师补充或确认的项。
- `internalRisks`：只供老师判断的风险提示，不能出现在学生/家长端。
- `visibilityAudit`：是否隐藏模型、供应商、内部字段、未复核内容和低置信结果。

### 系统兼容层

为了不破坏现有页面和接口，保留以下字段：

- `weeklyScore`
- `mastery`
- `strengths`
- `risks`
- `tone`
- `timeline`
- `publishedText`
- `narrative`

旧字段继续可读，但新 UI 优先读取 `publishedView` 和 `teacherReview`。

## 数据来源规则

允许进入正式档案的来源：

- 已发布或已完成的今日任务。
- 已经教师复核的批改提交。
- 已确认错题记录和订正状态。
- 已发布阶段报告。
- 已确认 AI 问答学习信号。
- 已确认课堂平板互动或老师备注。

禁止进入正式档案的来源：

- 低置信 OCR。
- `needsTeacherReview=true` 且未确认的批改结果。
- 只有 `provisionalScore` 的分数。
- 未发布的生成草稿。
- 模型原始输出、内部 prompt、供应商名称、接口地址、调试字段。
- 未经脱敏的家长电话、登录码、真实隐私字段。

## 生成与发布流程

1. 老师在教师端选择学生和周期类型，点击生成周档案或月度综合档案草稿。
2. API 按自然周或自然月读取该学生的任务、复核批改、错题、报告、问答和课堂记录。
3. 服务层组装 `generationContext.studentSignals` 和 `profileEvidencePack`。
4. AI 只输出严格 JSON 草稿；服务层执行 parse、normalize、validate、repair 和可见性检查。
5. 教师端展示结构化草稿和证据面板，老师可编辑公开展示文案，也可删除敏感内容。
6. 老师点击发布后，API 写入 `StudentProfile.snapshot`，`draftStatus=published`。
7. 学生端/家长端只读取 `publishedView` 和兼容的 `publishedText`，不读取 `teacherReview`。

## 多端展示

### 教师端

教师端学生档案页改为四块：

- 周档案/月度综合档案草稿与发布。
- 证据来源与样本限制。
- 重点科目与下一阶段辅导动作。
- 已发布档案历史。

教师端可以看到样本限制和待确认项，但不暴露密钥、模型配置或完整内部运行对象。

### 学生/家长端

学生档案主入口展示：

- 顶部成长概览。
- 周/月切换。
- 三科总览。
- 重点科目展开。
- 错题与订正闭环。
- 老师下一步。
- 家长下一步。
- 学习时间线。

学生/家长端不展示数据来源、样本限制、内部风险、模型名、供应商、低置信结果、未复核草稿或调试字段。

### 小程序复用

微信小程序后续复用同一 `publishedView` 结构。小程序只负责展示、展开和刷新，不在端侧拼接核心 prompt、证据包或复核规则。

## 测试与验证

第一版实现时至少补以下验证：

- 服务层测试：`weekly_growth` 和 `monthly_comprehensive_growth` 快照能从任务、已复核批改、错题、问答和课堂记录构建。
- 可见性测试：学生/家长端响应不包含 `teacherReview`、内部字段、模型信息和未复核内容。
- 发布流程测试：未发布草稿不进入学生端；发布后 `publishedView` 可见。
- 低置信拦截测试：低置信 OCR、未确认分数和 provisional 结果不进入正式档案。
- PDF 边界测试：期中、期末不出现在第一版页面周期类型中，后续只能通过教师确认后的 PDF 交付流程扩展。
- Web 类型检查：`npm.cmd run typecheck --workspace apps/web`。
- API 检查：`.\jh.cmd check:api`。
- 中文文案检查：`.\jh.cmd check:encoding`。

## 分阶段落地

### 第一阶段：结构化周/月成长档案

- 增加周档案和月度综合档案结构化快照。
- 增强 draft/publish/profile 的返回结构。
- 教师端展示周/月结构化草稿和证据层。
- 学生/家长端展示发布后的周/月成长档案。

### 第二阶段：单科详情和期中/期末 PDF

- 增加单科月度详情。
- 增加期中、期末 PDF 草稿生成、教师确认和家长发送流程。
- 支持从重点科目直接生成下一阶段练习或小测草稿。

### 第三阶段：正式归档和图像/文档输出

- 结合云文档或导出物做正式长期归档。
- 按已确认字段生成图文卡片或 PDF。
- 增加档案历史对比，但仍不做排名、预测分或升学风险。

## 第一版默认决定

- 第一版默认周期支持自然周和自然月。周档案用于日常反馈，月档案用于长期成长复盘。
- 期中、期末不做页面常规切换项，后续以 PDF 形式生成、教师确认后发送给家长。
- 教师端字段命名为“老师下一步”；学生/家长端展示为“接下来练什么”，避免让学生看到内部排课语气。
- 家长可执行动作统一命名为“家长配合建议”。
- 当前 Web 页面先保留旧三入口，在顶部新增综合成长档案，避免一次性替换影响已有联调入口。
