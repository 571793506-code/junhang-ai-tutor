# 模块能力契约与 Web 对齐设计

> 后续设计：2026-09-11 用户已确定生成与批改日常使用优先、暂不推进小程序，并认可 Astra 主处理、Flash 按需辅助、Sol 有限替补及对话＋结构化编辑工作台。见 [生成与批改日常工作台设计](2026-09-11-generation-grading-daily-workbench-design.md)。本文保留历史设计；模型默认策略是否已切换须以实现与验证为准。

**日期：** 2026-09-07

## 1. 目标

把 Codex 对话中已经采用的生成、批改、资源库和学生档案规则沉淀为项目内可复用的 Skills、API 契约和服务层流程，使 Web 端与服务层使用同一套上下文、模型路由、复核门禁和验证标准。

本设计解决四个问题：

1. Web 表单不能完整表达当前生成、批改和资料上下文要求。
2. Web 端部分功能仍停留在旧的展示或提交状态，没有消费服务层的结构化结果。
3. 模块 Skills 说明了原则，但对何时加载、依赖哪些模块、如何执行和如何验收还不够明确。
4. 生成、批改、资料和档案之间已有数据结构，但入口和状态没有形成一条稳定、可追踪的内部链路。

## 2. 范围

本阶段覆盖：

- 生成、批改、资源库、学生档案四个模块的能力契约和服务层边界。
- 根目录 `SKILLS.md` 和四个模块 Skills 的触发条件、依赖关系、输入输出、模型和验证规则。
- Web 端生成、批改、资源库、学生档案入口对现有 API/服务层结构化结果的对齐。
- Terra、MiniMax、Sol 和 DeepSeek 的任务路由、预算、升级和失败收口规则。
- 面向模块的契约测试、Skills 检查、API 检查、Web 类型检查和质量样本入口。

本阶段不覆盖：

- 电视大屏的正式实时聚合和投屏协议。
- 完整课堂投票、小队协作和复杂语音交互。
- 家长独立账号体系。
- 自动发布、自动归档或绕过教师确认的 AI 流程。
- 以小程序页面替代服务层逻辑。
- 更换当前模型供应商，或把 DeepSeek/MiniMax 扩展为默认文本生成链路。

## 3. 总体架构

四个模块共用以下数据流：

```text
教师目标
  -> 服务端目标与权限校验
  -> 教材/资源上下文与学生证据组装
  -> 模块服务调用模型或确定性处理
  -> parse / normalize / validate / repair
  -> 结构化草稿与审计状态
  -> 教师复核或确认
  -> 档案证据与学生/家长可见结果
```

Web、小程序和平板只提交必要业务字段并消费服务端返回的公共结构。角色权限、上下文组装、模型选择、结构修复、质量门禁、归档准入和可见字段过滤全部保留在 API、服务层、共享包或明确的契约中。

## 4. 统一模块能力契约

项目增加一份机器可检查的模块能力登记，至少描述以下字段：

- `moduleId`：`generation`、`grading`、`teaching-materials`、`student-profile`。
- `triggers`：用户意图、入口动作和需要加载的 Skill。
- `dependencies`：必须先准备的资料、答案、证据或教师状态。
- `requestContract`：允许提交的字段和服务端派生的字段。
- `resultContract`：学生、教师和内部角色分别可见的字段。
- `modelPolicy`：主模型、辅助能力、推理档位、超时、token 和升级条件。
- `reviewGate`：即时返回、教师复核、教师确认或禁止发布。
- `verification`：模块对应的最小检查、契约测试和质量检查。

登记内容供服务层、Web 状态面板和 Skills 文档引用。模型名、内部 prompt、预算和运行元数据只用于教师内部或服务器审计，不能进入学生、家长、课堂平板和公共屏响应。

## 5. Skills 路由设计

根目录 Skills 入口增加“意图 -> 首个 Skill -> 依赖 Skill -> 执行顺序 -> 验证命令”的路由表。

### 5.1 生成

```text
生成小测/练习/试卷/任务
  -> teaching-materials（声明教材或资料时）
  -> prompt-context-engineering
  -> generation
  -> 需要后续批改时保留 gradingSourcePackage
```

生成 Skill 必须说明 `kind` 分流、`generationContext` 必填结构、三科题型规则、答案包、教师复核、模型预算、Sol 升级和质量命令。生成结果永远是草稿，不能直接发布。

### 5.2 批改

```text
已生成材料批改
  -> grading
  -> 读取 gradingSourcePackage / questionLayoutManifest

外部材料批改
  -> grading
  -> 生成或登记参考答案
  -> 教师逐题复核
```

批改 Skill 必须明确 OCR、印刷题干、学生作答、答案来源、逐题分数和档案证据的分层关系。低置信、漏页、证据不足、模型冲突或未确认结果只能产生待复核草稿。

### 5.3 资源库

```text
资料上传或登记
  -> 转换/索引
  -> 来源与版本登记
  -> 教师审核
  -> 绑定教材/章节
  -> generationContext.teaching.contentContext
```

资源库 Skill 必须说明普通资料、`.edupdf`、版本匹配、来源范围、chunk 可见性和生成前审核门禁。Web 只显示摘要和状态，不显示完整 Markdown chunk。

### 5.4 学生档案

```text
已确认任务/批改/课堂记录/合格问答
  -> profileEvidencePack
  -> 样本和冲突判断
  -> 结构化档案草稿
  -> 教师编辑确认
  -> publishedView / printView
```

档案 Skill 必须说明证据优先级、样本不足、`blockedEvidence`、周/月档案和期中/期末 PDF 的差异。未确认批改和低置信结果不得进入公开档案。

## 6. 模型路由

保持当前模型分工，并由服务层统一决定：

| 场景 | 默认处理 | 失败处理 |
| --- | --- | --- |
| 学生/课堂问答 | Terra `low`，最多一次 | 不调用 Sol；不可用则返回不可用状态 |
| 今日任务与档案草稿 | Terra `low` | 结构失败后进入教师复核 |
| 小测、普通练习 | Terra `medium` | 最小失败分区一次 Sol `high` |
| 正式试卷、参考答案、主观批改 | Terra `high` | 证据充分且属于 availability/quality 故障时局部 Sol `high` |
| OCR、题目区域和语音 | MiniMax | 失败保留证据并进入教师复核 |
| 紧急文本回滚 | DeepSeek | 仅显式开启，不进入默认路由 |
| 客观题、总分、来源指纹 | 服务层确定性规则 | 不交给模型替代计算 |

配置、鉴权、模型不支持和证据不足不触发 Sol。Sol 后不串接第三个文本模型。所有模型输出仍须经过结构化校验、修复和教师复核。

## 7. Web 对齐要求

### 7.1 生成

Web 生成页必须提交服务端需要的目标、类型、教材/章节、知识点、难度、题量、教师要求和输出约束。页面显示上下文摘要、资料审核状态、生成进度、草稿审查状态、布局状态和正式导出资格；不自行拼接 prompt、计算答案包或判断模型质量。

### 7.2 批改

Web 批改页统一支持已生成材料和外部材料两条路径。工作台必须显示图片质量、页序、OCR 题目、学生作答、答案来源、置信度、逐题结果、教师修正和归档阻断原因。完成逐题确认后，才能写入错题和档案。

### 7.3 资源库

Web 资源页必须显示来源、类型、年级、科目、教材版本、章节、知识点、索引状态、教师审核状态和是否允许生成。上传、转换、索引、同步和审核动作都调用现有 API，不能在页面内重新实现资料解析和路径防护。

### 7.4 学生档案

Web 档案页必须以结构化快照为主，显示证据覆盖、样本不足、重点科目、错题闭环、教师下一步和家长建议。教师编辑和发布前保留复核清单；学生端只能读取已发布 `publishedView`，期中/期末只显示教师发送状态。

## 8. 错误和状态

所有模块统一区分：

- `available`：能力可用，可以继续操作。
- `draft`：已有结构化草稿，但仍需教师复核。
- `review_required`：证据、质量或资料状态要求教师确认。
- `blocked`：权限、教材、资料、图片或模型配置阻断。
- `failed`：任务未完成，保留可追踪错误和请求 ID。

学生端只显示温和的可用、处理中、等待老师查看和已反馈状态。教师端显示复核原因、来源和服务摘要。原始错误、模型路由、密钥、数据库信息和内部 prompt 只进入服务器日志或受限审计。

## 9. 分阶段实施

### 阶段一：能力契约与 Skills 路由

- 建立模块能力登记和共享字段命名。
- 更新根目录和四个模块 Skills。
- 增加 Skills 路由、路径、验证命令和跨模块依赖检查。
- 验证 Skills 检查、编码检查和现有服务测试。

### 阶段二：生成 Web 对齐

- 对齐生成输入和 `generationContext`。
- 对齐异步任务、草稿、布局、教师复核和答案包展示。
- 增加上下文预览和失败状态。
- 验证生成蓝图、API、Web 类型和生成质量样本入口。

### 阶段三：批改 Web 与档案证据对齐

- 对齐生成材料和外部材料两条批改路径。
- 完善 OCR/答案/逐题复核/归档阻断展示。
- 对齐 `profileEvidencePack`、教师复核和发布状态。
- 验证批改契约、角色过滤、档案门禁和 Web 类型。

### 阶段四：资源库与模型质量闭环

- 对齐资料上传、索引、来源审核和上下文注入。
- 统一模型能力状态、预算和失败分类。
- 建立真实 gold cases，分别评估 OCR、批改、生成和档案摘要。
- 质量结果满足教师设定的生产门槛后，再讨论未完成的端侧和公共屏整改。

## 10. 成功标准

本设计实施完成后，应满足：

1. Codex 能根据用户意图选择正确 Skill，并知道前置依赖、执行顺序、输出字段和验证命令。
2. Web 生成、批改、资源库和档案入口不再绕过服务层结构化契约。
3. 生成结果可被批改直接引用，批改确认结果可被档案证据包使用。
4. 资料审核状态能阻断不合规生成，并能追踪上下文来源。
5. 学生、教师、课堂端和内部审计看到不同的字段集合。
6. 模型失败会按 availability、quality、evidence 和 configuration 分类收口。
7. 没有教师确认的生成、批改和档案结果不会进入正式发布或学生/家长可见范围。
8. 每个阶段都有独立的契约测试和验证命令，不依赖一次完整 E2E 证明所有质量。
