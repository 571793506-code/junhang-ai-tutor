`AGENTS.md` project rules take priority. Before editing, read the `skills/generation/SKILLS.md` Playbook. For cross-module changes, read every affected module Playbook.

When a request names a textbook or teaching material, load `skills/teaching-materials/SKILLS.md` first, then `docs/41-prompt-context-engineering-playbook.md`, then this Playbook. If the generated material will be graded, preserve `gradingSourcePackage` and load `skills/grading/SKILLS.md` for the downstream review boundary.

Minimum verification: `cmd /c npm.cmd run check:generation:blueprint`.

For daily quality regression, `fixtures/quality/generation-confirmed-calculation.json` preserves the existing teacher-reviewed four-question sample; `packages/services/src/generation-confirmed-regression.test.mjs` exercises scope, exact answers, analysis and rubric preservation through the shared service using a mocked model. This is offline regression, not a new generation, live model quality result or permission to confirm another draft. Its result-only awards are 1/1/1/1; the separate earlier remediation sample retains its confirmed 2/2/1/1 awards. Teacher request determines future quantity, grade and knowledge points.

Read `skills/generation/references/runtime-rules.md` for the shared teaching rules. Change teaching details there, then verify `cmd /c npm.cmd run check:skills`. Runtime loading belongs in the AI layer; never accept a rule path or prompt from a client. Model routing and budgets belong in `packages/ai/src/model-policy.js`.

For remediation, consolidation or reassessment, preserve the teacher's explicit stage in `requirement` or each day's goal and use the runtime rules section `补弱、巩固与复测`. Do not invent a new purpose value, infer current mastery from old mistakes, or adopt a reference worksheet's count. Check process rubrics for carry-forward errors and result-only credit before presenting a draft; new scoring proposals do not rewrite confirmed source packages.

For shared workflow commands, read the "Shared workflow API and CLI" section of `docs/14-api-contract.md` and the current implementation plan before using `node scripts/teaching-workflow.mjs`. Use an existing authenticated teacher session through `TEACHING_SESSION_FILE`; never write the database directly or invent confirmation fields. The current local deployment completed schema migration and persistence enablement on 2026-09-29; the teacher-confirmed assessment passed real Web publication and both formal PDF exports on 2026-09-30. Check the current service rather than assuming all deployments are enabled. See `docs/teaching-workflow-acceptance.md` for verified scope and deferred holdout tasks; resume remains unavailable. Fill structured subject, grade or student, kind, purpose and requirement from the confirmed conversation. Use requestedItemCount for task and per-day counts. For a natural-language revision, send selected targetQuestionIds and instruction; preserve expectedRevision and operationKey. Treat needs_input as incomplete and 503 as unavailable. Newly discovered materials must pass registration/approval before entering task context.

To publish an already teacher-confirmed assessment version, GET the workflow and use `assignment --id <id> --input <json>` with only `expectedRevision`. This adapter is enabled in the verified local deployment. Reuse server-recorded confirmation; an uploaded JSON cannot confer approval. The command returns an Assignment ID, not PDFs. Use that ID with the existing draft-export and print-export APIs; content confirmation persists through preview, but formal export still requires valid layout and both PDFs. Do not use legacy draft-review or answer-source import to modify a published version; revise and confirm in the workflow, then publish a new Assignment. Preserve the original revision on replay and read conflicts before proceeding. Explanation publication is not supported yet.

For `purpose: explanation`, read `content.explanation` (concept, steps, workedExamples, commonMistakes), not questions. Use the same CLI `command` with `targetExplanation: true`: revise with instruction, or with a complete `replace_explanation` patch; confirm only after the teacher explicitly approves the whole explanation. Do not mix targetQuestionIds into these commands. Edits revoke explanation confirmation; replay preserves the original operationKey and expectedRevision. GET a historical version before restoring it. Server-recorded confirmation may be reused on restore only after current validation. Confirmation does not publish a lecture, create an answer package or export PDFs. Web uses this same contract; when the service is unavailable, retain the legacy generation entry. Cancelled tasks are read-only and cannot be resumed or restored; a new task requires a deliberate new requestKey. Never enable the persistence switch just to make a browser test pass.
